# Dizal — تكامل واتساب

## 1. المبدأ

لا نربط النظام بمكتبة واتساب مباشرة من كل Route.

ننشئ Provider Adapter.

الـService ينفذ:
send_text
send_document
send_template
check_health

ثم Provider هو الذي يقرر كيف يرسل.

## 2. Providers المستهدفون

يمكن دعم:
- Baileys Gateway.
- WhatsApp Cloud API.
- HTTP API خارجي.

الهدف أن لا يتغير Domain Logic عند تغيير المزود.

## 3. إعداد واتساب

المدير يرى:
- Provider.
- Enabled.
- API URL.
- Token.
- Sender.
- Webhook secret.
- Timeout.
- Retry limit.

Token لا يظهر كاملًا بعد الحفظ.

## 4. الإرسال

يجب أن يذهب الإرسال عبر Queue/Outbox وليس أن يتوقف الطلب HTTP حتى ينجح الإرسال في كل مرة.

الحالات:
queued
sending
sent
failed
retrying
cancelled

## 5. الرسائل

قوالب:
- اعتماد مزارع.
- رفض مزارع.
- طلب استكمال.
- اعتماد توريد.
- رفض توريد.
- تنبيه دين.
- تنبيه اقتراب السقف.
- تسوية مستحقة.
- إشعار للمدير.
- إرسال سند.

## 6. المرفقات

يمكن إرسال:
- PDF.
- صورة.
- مستند.

ولا يسمح بإرسال ملف لا يحق للمستخدم الوصول إليه.

## 7. سجل الرسائل

كل رسالة:
- المستلم.
- المستخدم الذي أنشأها.
- القالب.
- نص الرسالة.
- الحالة.
- وقت الإرسال.
- معرف المزود.
- خطأ المزود.

## 8. Retry

التجربة:
- محاولة فورية.
- ثم retry بزمن متزايد.
- حد أقصى.
- بعدها تظهر الرسالة كفشل وتحتاج متابعة.

## 9. Webhook

إذا دعم المزود Webhook:
يتم تحديث:
- sent.
- delivered.
- read.
- failed.

مع تحقق من secret.

## 10. OTP مستقبلي

يمكن استخدام واتساب لتسجيل الدخول أو تأكيد رقم الهاتف في نسخة لاحقة.

لكن لا يجب أن نجعل OTP شرطًا على كل المستخدمين منذ النسخة الأولى إذا كان هناك نظام اسم مستخدم وكلمة مرور يعمل بالفعل.
